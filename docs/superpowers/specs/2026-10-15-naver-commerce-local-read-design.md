# 네이버 커머스API 로컬 인증·조회 연동 설계

상태: **2026-10-15 설계·구현계획/Native 승인. 로컬 구현·보호 API·외부 상태 UI 배포 완료. 사용자 부재로 앱/키 설정과 실제 API 인증·저장 검증은 대기 중.**

## 목적과 승인 범위

사용자는 스마트스토어 승인 완료를 알렸고, 기존 Seller OS에 인증·스토어 조회 연동을 요청했다. 2026-10-15 호출 위치를 **새 호스팅 비용 없는 현재 PC 서버**로 선택했다.

완료 결과는 운영자가 자신의 스토어를 인증·조회하고, 기존 외부 대시보드에서 스토어명/연결 확인 결과/마지막 조회 시각을 확인할 수 있는 것이다. 상품 등록·수정·삭제, 주문·배송·취소·정산 작업은 범위 밖이다. 기존 후보의 HOLD/NOT_PUBLISHED 상태를 해제하지 않는다.

## 확인한 현재 상태와 선택 이유

- 기존 코드에는 Naver Search API 경쟁상품 조사만 있고 Commerce 인증 클라이언트는 없다. Search API의 NAVER_CLIENT_ID/SECRET을 Commerce에 재사용하지 않는다.
- 실제 커머스API센터 로그인 및 대상 스토어 접근을 확인했다. 기존 내 스토어 앱은 없으며, 등록 양식에는 이름/설명/호출IP(최대3개)/API그룹/토큰 표준 확인 항목이 있다. 등록은 제출하지 않았다.
- 네이버는 사전 등록한 실제 호출 기기의 공인 outbound IPv4만 허용하고 IPv6는 지원하지 않는다. PC의 공인 IPv4가 바뀌면 등록을 갱신해야 한다. 고정 IP나 영구 무중단 운영을 보장하지 않는다.
- Supabase Edge Functions는 고정 출발 IP를 제공하지 않으므로 직접 Naver 호출 방식은 제외한다. Pages 도메인, Supabase DB IP나 일시적인 Edge IP를 대신 등록하지 않는다.
- 별도 고정IP 서버/프록시는 운영 비용·권한이 추가될 수 있어 이번 범위에서 제외한다. Oracle 자동매매봇, 다른 프로젝트, 기존 도메인/DNS를 재사용하거나 변경하지 않는다.

## 구성과 데이터 흐름

1. 로컬5173대시보드에서 로그인한 운영자가 **인증·조회 확인**을 명시적으로 요청한다.
2. 같은 PC의 Vite 서버가 origin/host/요청 형식/사용자 인증/고정 workspace의 owner 권한을 검증한다. 검증 전에는 Naver 요청을 하지 않는다.
3. 로컬 서버가 서버 전용 환경변수의 Commerce 자격증명으로 토큰을 얻고, 계정과 채널을 읽는다. 최초에는 운영자가 조회 결과를 실제 스토어와 대조해 채널 결합을 확인한다.
4. 확인된 채널을 로컬 workspace 설정에 고정한 후에만, 제한된 결과를 기존 Supabase Seller OS 영역에 저장한다. 다른 채널이 반환되면 결합 오류로 중단한다.
5. 외부 Pages는 자신의 workspace에 저장된 결과만 읽는다. PC·localhost·CDP·Naver 토큰에 직접 접근하지 않는다. 외부 화면의 새로고침은 저장 결과를 다시 읽는 동작이며 Naver 재조회를 의미하지 않는다.

현재 단계는 수동 확인 1회/재확인 방식이다. 외부 명령 대기열, 상시 동기화, 자동 시작, 장기 실행 세션은 추가하지 않는다. 기존1688작업자와 독립된 얇은 로컬 어댑터를 두며 기존 수집을 중지하거나 설정을 공유하지 않는다.

## 허용하는 Naver 호출

호스트는 `https://api.commerce.naver.com` 한 곳으로 고정하고, 아래 세 요청만 허용한다. 임의 URL/path/method/account_id를 클라이언트 입력으로 받지 않는다. 리다이렉트는 따르지 않는다.

| 목적 | HTTP 경로 | 제한 |
| --- | --- | --- |
| 자신의 앱 인증 | POST /external/v1/oauth2/token | form-urlencoded, grant_type=client_credentials, type=SELF |
| 자신의 계정 확인 | GET /external/v1/seller/account | 인증 토큰의 계정만 조회 |
| 자신의 스토어 채널 확인 | GET /external/v1/seller/channels | 확인·고정한 STOREFARM 채널만 사용 |

인증은 발급 직전 생성한 밀리초 timestamp와 공식 bcrypt 전자서명 절차를 사용한다. 인증 요청의 POST는 토큰 발급에만 허용되는 예외이며, 모든 판매/설정 변경 요청은 클라이언트 코드 수준에서 거절한다. '판매자정보' API 그룹에는 쓰기 기능도 포함되므로 그룹 이름만으로 읽기 전용이라고 주장하지 않는다.

신규 bcrypt 의존성은 현재 공식 npm registry에서 조회한 `bcryptjs@3.0.3`으로 정확히 고정하고 lockfile을 함께 갱신한다. 이 문서 작성 시에는 설치하지 않았다. Supabase SDK는 기존 고정 버전을 유지한다. 공식 예제와 호환되는 서명을 테스트한 후에만 실 키로 검증한다.

토큰은 메모리 캐시만 사용하며 expires_in 이전에 만료 처리한다. 디스크·DB·브라우저·채팅·로그에 저장하지 않는다. 매 API 호출마다 재발급하지 않으며 한 번의 확인 작업을 중복 실행하지 않는다. 사용자 요청은 workspace당 최소60초 간격으로 제한하고, 401 재인증은 최대1회, 자동 재시도는 그 이상 하지 않는다. 각 외부 요청은20초/응답64KiB, 전체 확인 작업은45초로 제한하며 남은 전체 제한 시간을 우선한다. 429는 무한 재시도하지 않고 다음 수동 확인을 안내한다. 로그아웃·사용자 전환·요청 취소는 로컬 작업 epoch도 무효화하고, 취소된 작업은 추가 조회·클라우드 게시를 하지 않는다.

## 자격증명과 최초 채널 결합

- 기존 Git무시 로컬 환경 파일에 별도 NAVER_COMMERCE_CLIENT_ID/SECRET만 보관한다. 실제 이름/배치와 읽기 범위는 구현계획에서 고정한다. `VITE_`로 시작하는 자격증명 변수는 금지한다.
- Supabase 서비스 역할 키를 PC에 새로 복사하지 않는다. 로컬 사용자의 기존 Supabase 세션으로 workspace 권한을 확인하고, 기존 보호 서버를 통해 정제 결과만 저장한다.
- Commerce 앱은 선택된 스토어 전용으로 생성한다. 초기 권한은 판매자정보만 신청하며 상품/N배송·문의·주문·정산은 추가하지 않는다. 공인IP 확인/네이버 등록과 최종 권한·약관 확인은 사용자에게 실제 값을 보여준 뒤 진행한다.
- 비밀키는 사용자가 로컬 비밀 설정에 직접 입력한다. 에이전트가 채팅·스크린샷·일반 문서로 전달받거나 UI에 표시하지 않는다. 새 키 생성/기존 키 교체/복구도 사용자가 확인한다.
- 최초 성공 조회는 `확인 필요`이며 바로 '연결 확인'으로 저장하지 않는다. 로컬 화면의 채널명/채널 번호/URL을 운영자가 실제 스토어와 대조해 확인하면, 서버의 고정 workspace+예상 채널 번호 결합을 로컬 설정에 저장한다. 이후 불일치는 연결 실패로 취급하고 정상 스냅샷을 덮어쓰지 않는다.
- 채널 번호는 정수 정밀도를 잃지 않는 문자열로 보관한다. 안전 정수가 아닌 숫자 응답은 조용히 반올림해 사용하지 않고 오류로 처리한다.

## 클라우드 저장과 권한 경계

기존 프로젝트에 Seller OS 전용 연결 스냅샷 테이블을 추가한다. 논리적 키는 workspace_id이며 Naver 비밀값은 어떤 열에도 저장하지 않는다.

저장 허용 항목은 provider/source, workspace, 고정 채널 번호, 스토어명/HTTPS URL, 마지막 시도·성공 시각, 상태·정제된 오류 코드, 작성자·revision뿐이다. source는 `LOCAL_WORKER_REPORTED`로 표시한다. Naver 원본 JSON, 판매자 개인정보/주소/전화/사업자번호, 전체 계정UID, 요청 헤더/서명/키/토큰, 공인IP는 클라우드 스냅샷에서 제외한다.

기존 Edge API에 정제 결과 저장/조회 action만 추가한다. 기존 exact-origin 허용목록과 JWT/getUser/owner membership 검사를 재사용한다. workspace는 로컬 고정 설정 및 인증된 요청과 일치해야 한다. payload는 알려진 필드/상태만 허용하고 중첩된 임의 데이터도 거절한다. 서버 수신 시각·작성자·revision은 클라이언트가 정하지 않는다. 이전 revision/지연 응답은 최신 결과를 덮어쓰지 못한다.

새 테이블은 RLS와 명시적 grant를 함께 설정한다. anonymous 접근을 차단하고 authenticated direct write는 허용하지 않는다. 읽기는 해당 workspace owner에게만 허용하며, 쓰기는 기존 보호 서버가 검증한 뒤 workspace를 한정해 수행한다. 다른 앱 테이블·기존 Auth·멤버십·키·과거 후보는 변경하지 않는다. 새 테이블 노출 정책 변화도 실제 프로젝트에서 확인한다.

이 스냅샷은 **운영자의 인증된 로컬 작업자가 보고한 마지막 조회 결과**이지 Supabase가 Naver에 직접 확인한 실시간 증명이 아니다. 소유자가 조작한 보고만으로 상업적 행동을 허용해서는 안 된다. 향후 판매 기능이 생겨도 별도 실 인증/검토가 필요하며 이번 연동 상태를 판매 승인 조건으로 재사용하지 않는다.

## 기존 UI에 표시할 상태

기존 설정 → API 키 탭의 네이버 행을 실제 연결 상태 카드로 교체한다. 레이아웃/탭/다른 API 행은 유지하며, 가짜 키 끝자리나 작동하지 않는 연결 버튼으로 연동됐다고 오해시키지 않는다. 새 네이버 비밀키 입력창은 외부 사이트에 만들지 않는다.

| 상태 | 표시와 동작 |
| --- | --- |
| 설정 없음 / 아직 미검증 | 실제 인증한 적이 없음을 표시. '스토어 승인' 사용자 알림만으로 연결 처리하지 않음 |
| 최초 채널 확인 필요 | 로컬에서 실제 조회한 채널을 운영자가 대조. 확인 전 결과는 정상 연결로 게시하지 않음 |
| 최근 인증·조회 확인 | 계정+채널 조회/고정 결합/클라우드 저장 모두 성공한 마지막 시각을 표시 |
| 오래된 확인 | 마지막 성공 후15분이 지나면 stale로 표시. 기존 시각·결과는 보존하고 실시간 정상이라고 표시하지 않음 |
| IP 거절 / 인증 실패 / 권한 부족 | 정제 오류를 구분. 최신 시도 실패가 기존 성공을 현재 정상으로 가리지 않도록 표시 |
| 클라우드 저장 실패 | 로컬에서 확인 성공과 저장 성공을 구분하고 '동기화 미완료' 표시. 외부는 이 실패 자체를 알 수 없으므로 마지막 서버 수신 시각/이전 결과와 오래된 상태를 표시 |
| PC 상태 확인 불가 | 외부 화면에서는 PC가 켜졌는지 단정하지 않고 마지막 저장 시각을 표시. 로컬 호출 버튼은 제공하지 않음 |

로컬에만 '인증·조회 확인'을 제공한다. 외부에는 '저장 결과 새로고침'만 제공한다. 로그아웃/사용자 전환 시 대기 중 응답은 폐기하고 화면을 비운다. 기존 조사 패널의 '스토어 심사 대기' 문구는 사용자 승인 보고와 실제 Commerce 연결 상태를 구분한 사실적인 안내로만 바꾼다. 판매자 계정 조회 API가 제공하지 않는 스토어 심사 상태나 수요를 만들어 표시하지 않는다.

## 검증과 완료 기준

구현은 승인된 구현계획의 TDD로 진행한다. 최소한 다음을 확인해야 한다.

- 공식 bcrypt 서명/표준 form 요청, SELF 모드, 토큰 만료/단일 재발급/시간 초과/크기 제한/429 제한.
- localhost origin/Host와 owner 권한 확인 전 upstream 요청0건. 미로그인/가짜 세션/다른 workspace/비owner/임의URL/쓰기 action은 거절.
- 승인한 채널과 다른 응답, 미확인 최초 채널, 비정밀 숫자 ID, 잘못된 응답을 정상 연결로 저장하지 않음.
- DB/응답/로그/클라이언트 번들에 키·토큰·원본 개인정보가 없음. 새 RLS/grant의 anonymous·타 workspace 차단과 owner 조회를 실제 검증.
- 최신/오래된 상태, 실패 후 기존 성공 보존, 동기화 실패, 지연 응답·로그아웃 처리, 외부에서 localhost 호출0건.
- 실제 승인된 앱/등록IP로 토큰 발급+두 GET 성공, 운영자 채널 확인, 로컬 저장, 외부 로그인/조회/전체 새로고침을 모두 통과해야 '연결 완료'라고 보고.
- npm test 전체, 깨끗한 분리 설치, build, diff검사와 실제 브라우저 검증. 기존6후보/revision/HOLD/NOT_PUBLISHED 보존. Commerce 상품/주문/배송/설정 변경 요청0건.

아직 앱/키가 없으므로 실 인증 결과는 현재 검증하지 않았다. 모의/단위 테스트만으로 실 연동 완료를 주장하지 않는다.

## 배포·비용·롤백

구현은 기존 전용 작업브랜치에서 진행한다. Supabase는 Seller OS 전용 변경만 배포하고, Pages는 검증된 dist만 수동 업로드한다. PC 서버는127.0.0.1:5173을 유지하며 터널/포트포워딩/원격CDP를 만들지 않는다. 유료 리소스나 다른 프로젝트 변경이 필요하면 중단하고 별도 승인을 받는다.

롤백은 로컬 어댑터 중지/비밀 설정 제거와 이전 검증 프런트/Edge 재배포다. 새 스냅샷 테이블은 즉시 삭제하지 않고 이력을 보존한다. 기존 후보·Auth·다른 앱을 초기화하지 않는다. 앱 사용 중단·키 폐기는 사용자가 네이버에서 별도 확인하며, 무관한 앱의 키를 변경하지 않는다.
