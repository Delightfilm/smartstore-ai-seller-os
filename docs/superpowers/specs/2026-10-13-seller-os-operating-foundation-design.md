# Seller OS 운영 기반 설계

작성일: 2026-10-13 · 상태: 사용자 문서 검토 대기 · 기준 커밋: e0bb8d8

## 승인된 목적과 경계

- 해외구매대행 전용. 사용자 요청 범위는 운영 기반 → 상품 조사 자동화 → 비용 검증 → 심사 → 상세페이지 준비(1~5단계).
- 기존 SmartStoreSellerOS 메인 UI/레이아웃과 별도 /sourcing-console 경로 유지. 인증/실데이터 연결만 필요한 지점에서 변경한다.
- 새 Supabase 조직과 Seller OS 전용 새 프로젝트 사용. 기존 DF-AUTOSYNC 조직과 그 프로젝트에는 설정, 데이터, 멤버, 과금, 이전 작업을 하지 않는다.
- 신규 조직 표시 이름 제안: Seller OS. 신규 프로젝트 이름 제안: seller-os. 새 조직 ID를 실제 생성 결과로 확인하며 이름만으로 기존 프로젝트를 선택하지 않는다.
- 유료 요금제, 추가 리소스, 외부 AI/유료 데이터 API 등 비용 발생 작업은 사전 승인 전 실행하지 않는다. 무료 한도가 부족하면 기존 프로젝트를 중지/삭제/이전하지 않고 사용자에게 알린다.
- 실제 상품 등록, 1688 구매/결제, 배송 신청/수정/폐기, 고객정보 전송은 범위 밖. main 병합/실서비스 배포도 별도 승인 대상이다.

## 현재 사실

- 후보 데이터는 개발 서버의 .seller-os/candidates.json에 저장된다. 실제 클라우드 DB/로그인은 없다.
- 조사 패널은 개발 환경에서만 제공된다. 메인 매출/주문 등은 mock 데이터다.
- P2013은 초기 조사 데이터이며 실시간 공급/포장/운임 확인이 아니다. HOLD를 유지하고 승인된 상품으로 바꾸지 않는다.
- 로컬 인증 브라우저는 127.0.0.1:9222의 사용자 세션이다. 클라우드 서버에서 이 주소로 연결할 수 없다.
- 기존 검증 기록은 40개 테스트와 빌드 PASS이며, 이번 설계 문서 자체가 새 구현/운영 검증을 의미하지 않는다.

## 단계 구분

이 문서는 첫 하위 프로젝트인 **운영 데이터 기반**을 구현 가능한 범위로 정의한다. 2~5단계는 아래 계약을 따르되 각각 설계/구현/검증을 이어서 수행한다. 문서 하나로 모든 단계가 구현됐다고 보고하지 않는다.

1. 운영 기반: 전용 DB·실제 로그인·권한·후보/이력 저장·기존 데이터 이전·백업 복구.
2. 조사 자동화: 공통 상품 형식, MOQ 1 및 SKU 포장 데이터 검증, 중복 제거, 갱신 작업과 수집기 상태.
3. 비용 검증: 출처/유효일/추정 여부가 있는 비용 모델, 퀵스타의 허용된 조회 연동. 요금 조회 기능이 문서로 확인되지 않으면 임의 API를 만들지 않는다.
4. 심사: 근거와 비용 버전에 묶인 통과/보류 판정, 만료/변경 시 재검토. 사용자의 단순 체크만으로 불완전한 증거를 통과시키지 않는다.
5. 상세페이지: 검증된 상품 사실과 사용권 확인 이미지로 생성, 미리보기/검수/내보내기. 미검증 수치·효능·인증·배송 약속은 생성하지 않는다.

## 운영 기반 아키텍처

- 기존 React/Vite 화면 유지. 로그인 화면은 Supabase Auth로 연결하고 실제 사용자의 인증 상태로만 데이터에 접근한다.
- 신규 전용 Supabase의 Postgres에 후보/검토 이력을 저장한다. 클라이언트는 공개용 키와 사용자 세션만 사용한다. service role/비밀키는 브라우저나 Git에 두지 않는다.
- 공개 회원가입/익명 로그인은 운영 접근 경로로 사용하지 않는다. 첫 사용자 계정은 사용자 본인이 확인한 계정으로 설정하고, 운영 멤버십은 서버 관리 경로에서만 부여한다.
- 각 데이터에 workspace_id를 기록하고 workspace_members로 접근을 제한한다. 첫 단계는 사용자 한 명의 owner 운영이며, 다른 역할/초대 UI는 추가하지 않는다.
- 모든 노출 테이블에 RLS와 최소 권한 적용. 사용자 편집 가능한 user_metadata는 권한 근거로 쓰지 않는다.
- 승인 상태, 감사 이력, revision은 클라이언트가 임의 수정하지 못한다. 허용된 입력만 받는 원자적 저장 경로에서 revision 비교와 이력 추가를 한 트랜잭션으로 처리한다.
- 클라우드 미설정 시 기존 로컬 자료를 보존하되 mock 로그인으로 클라우드 기능에 진입하는 우회 경로를 만들지 않는다. 로컬/클라우드 모드를 화면에 명시하며 조용한 저장소 전환은 하지 않는다.

## 첫 단계 저장 모델

- workspaces: 운영 공간 식별자/표시 이름/생성일.
- workspace_members: 공간-인증 사용자 연결과 owner 역할. 일반 클라이언트의 멤버 추가/역할 변경 금지.
- candidates: 공간 ID, 소스, offerId, revision, 상품/옵션 자료, terms, market, research, review, listing, 생성/수정 시각. 기존 객체 형식은 검증된 JSON 필드로 보존하여 불필요한 전면 변환을 피한다.
- candidate_events: 공간/후보/행위자/서버 시각/이벤트 종류/변경된 필드와 근거 버전. 일반 사용자는 읽기만 가능하며 수정·삭제할 수 없다. 토큰·쿠키·비밀값은 기록하지 않는다.
- unique(workspace_id, source, offerId)로 후보 중복을 막는다. SKU 단위 데이터는 상품 옵션에 연결하며 단계 2에서 표준 형식을 확정한다.
- 고객 주문/개인통관정보는 이번 데이터 모델에 포함하지 않는다. publication은 미등록 상태를 유지하며 발행용 API를 추가하지 않는다.

## 데이터 이전과 기존 UI

- 로컬 파일을 먼저 백업하고 형식 검증/미리보기 후, 사용자가 확인한 workspace로만 이전한다. 기존 파일은 삭제하지 않는다.
- 동일 후보 재실행은 중복 생성하지 않는다. 이미 수정된 클라우드 후보를 로컬 데이터로 덮어쓰지 않고 충돌을 보여준다.
- P2013의 HOLD·근거 시각·가격 가정, 기존 케이블 후보의 미확인 상태를 그대로 이전한다.
- 후보 수/보류 수 등 조사 관련 지표를 실제 자료로 연결한다. 승인되지 않은 매출·주문 영역은 '미연동'으로 표시하며 mock 숫자를 실적처럼 표시하지 않는다.
- 다른 로그인 세션/기기에서도 동일 후보와 검토 이력을 조회한다. 충돌 시 미저장 내용을 보존하고 최신 자료 재조회·취소 선택을 제공한다.

## 백업·복구

- Free 플랜에서 관리형 자동 백업을 당연히 제공한다고 가정하지 않는다. 실제 플랜 기능을 확인하고 비용 없이 가능한 별도 내보내기/복구 절차부터 검증한다.
- DB 후보와 이벤트를 인증된 서버 관리 경로에서 버전·개수·해시 포함 형태로 내보낸다. 로컬 비공개 폴더에 저장하고 Git에 포함하지 않는다.
- 백업 검증은 격리된 테스트 환경 복구 후 후보 개수/ID/상태/이력을 비교한다. 인증 비밀/비밀번호나 세션 토큰을 업무 데이터 백업에 섞지 않는다.
- 초기 백업 목표: 매 작업일 종료 시점과 데이터 이전 직전. 자동 실행은 실행 호스트와 저장 위치를 확인한 뒤 설정하고, 실행되지 않은 스케줄을 완료로 보고하지 않는다.
- 복구 대상은 우선 업무 데이터다. Auth 계정·파일까지 포함한 완전 재해복구와 실제 복구 소요 시간은 별도로 검증하기 전 보장하지 않는다.

## 2~5단계와 연결할 안전 계약

- 수집기: 초기에는 사용자가 로그인한 PC에서 실행하고 승인된 서버 저장소로 결과를 보낸다. 쿠키/브라우저 프로필은 전송하지 않는다. 오프라인/캡차/로그인 만료는 대기 상태로 기록하고 우회하지 않는다.
- 서버/로컬 양쪽에서 지원하는 1688 URL을 검증한다. 임의 URL 탐색·무제한 재시도·동시 중복 작업을 금지한다.
- '포장 정보 완비'는 선택 SKU의 개당 포장 총중량과 가로/세로/높이, 단위, 근거 URL/관찰시각을 포함한다. 제품 순중량·박스당 묶음중량·다른 옵션 자료는 대체하지 않는다.
- 모르는 값은 null이며 0원/0g으로 해석하지 않는다. MOQ·재고·비용·경쟁제품 구성의 불확실성을 별도로 표시한다.
- 퀵스타 인증 종류/tokenKey/apiName/스키마/호출 한도/테스트 환경 확인 후 읽기 전용 호출만 허용한다. 발송·결제 기능과 고객 데이터는 연결하지 않는다.
- 비용 입력은 observed/quoted/estimated 출처와 시각을 유지한다. 부가비용·VAT·반품·광고 가정은 실제 청구액으로 위장하지 않는다.
- 검토 결과는 evidence_revision에 연결한다. 가격/옵션/포장/비용/권리 근거 변경 시 이전 통과를 해제한다. 소스에서 확인 못한 수요/리뷰를 추정 판매량으로 단정하지 않는다.
- 상세페이지 자료에 각 주장과 원본 근거의 연결을 유지한다. 권리 미확인 사진을 복제·재가공해 사용 가능한 것으로 취급하지 않는다.

## 필수 검증과 완료 기준

1. npm ci/test/build 및 기존 로컬 후보 흐름 회귀 테스트 통과.
2. 새 조직/프로젝트 ID·Free 요금·비용 결과 확인. 기존 조직/프로젝트에 쓰기 요청 0건.
3. 인증 없이 데이터 읽기/쓰기 거부. 비멤버 접근, 다른 workspace 접근, 자기 권한 상승, 위조 revision/판정 거부.
4. 저장과 이벤트 기록의 원자성 및 동시 수정 충돌 검증. 네트워크 실패 후 중복 저장/이력 누락이 없어야 한다.
5. 기존 두 후보 이전·재실행·사용자 편집 보존 검증. 두 독립 로그인 세션에서 저장/조회 일치.
6. 백업 복구와 무결성 비교 실증. 수행하지 못하면 '백업 구현'과 '복구 검증 완료'를 분리해서 보고.
7. 원래 레이아웃/메뉴/별도 실험 경로 유지, mock 표시 오인 방지, 로그아웃 후 데이터 접근 차단을 브라우저에서 확인.
8. 비밀값 유출/권한 정책 점검과 실제 서버 접근 테스트. 실제 상품/배송/결제 요청 0건.
9. main 병합/배포 승인 전에는 로컬·테스트 환경 검증까지만 보고. 다른 실제 기기나 배포 주소를 확인하지 못하면 다기기 운영 완료로 보고하지 않는다.

## 실패·롤백 원칙

- 비용/권한/로그인/연결 제한이 발견되면 원인을 기록하고 필요한 사용자 행동을 요청한다. 기존 서비스 재사용은 대안으로 임의 선택하지 않는다.
- 스키마 변경은 신규 전용 프로젝트에서만 버전 관리한다. 개발 중 실패 복구도 데이터 손실 없는 전진 수정부터 검토한다.
- 소스 롤백은 별도 revert 커밋. 클라우드 데이터/조직/프로젝트 삭제는 별도 승인이 필요하다. 로컬 후보 원본과 백업은 유지한다.
